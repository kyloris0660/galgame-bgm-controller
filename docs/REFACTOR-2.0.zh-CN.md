# 2.0 重构与交付报告

日期：2026-09-25。原始代码基线：`b53c418`。本次目标是解决应用选择困难、多游戏互相牵连，以及音频设备变化和退出恢复不可靠的问题。

## 1. 交付结果

- 删除推荐、评分、前台优先标记及全部后台进程列表。
- 选择器改为任务栏应用图标网格，支持搜索、多选、刷新、已添加标识和文件添加。
- 一个控制服务管理多个独立游戏状态；每个运行中的已登记 exe 有自己的托盘图标。
- 支持单游戏暂停、单游戏规则和“停止此游戏控制（本次）”；A 关闭或停止控制不影响 B。
- 音频按完整 exe 路径匹配，覆盖所有可用播放设备，持续发现新会话并处理设备重连。
- 记录并恢复接管前的静音状态，加入原子恢复记录、单实例保护和 UI 线程队列。
- 沿用 PyInstaller 文件夹 GUI、单文件 GUI 和 CLI 三种产物。
- 已更新桌面原快捷方式，从最终版本目录实际启动新版；保留原配置和旧版文件。

## 2. 原架构审查

原项目已有 policy、focus、audio、service、config、picker、tray 的分层雏形，不需要换框架才能解决问题。主要缺陷发生在各层之间的状态和生命周期边界：

| 部位 | 原问题 | 新实现 |
| --- | --- | --- |
| 选择器 | process_iter 枚举所有进程；“推荐”只是评分/高亮；路径占据主体 | 按 Win32 任务栏窗口条件枚举，按完整路径聚合；图标和短名称为主体 |
| 托盘 | 从 muted_list 中取第一个游戏，只有一个动态图标 | exe → Icon 映射，逐游戏创建、更新、退出；无受控游戏时有管理入口 |
| 运行状态 | 不运行的配置目标也进入策略快照 | 只有正在运行的目标进入快照；退出、重启会改变图标生命周期 |
| 进程扫描 | 每个目标重复遍历全部进程和窗口 | 每轮一次进程遍历和一次任务栏窗口遍历 |
| 音频发现 | 策略未变化就不执行；晚出现/重建的会话可能漏控 | 每轮重新枚举设备和会话，策略不变也会接管新会话 |
| 设备变化 | 只取默认设备的会话 | 枚举所有 ACTIVE 的 render 端点；每轮重建枚举器 |
| 音频身份 | 精确路径失败后按 exe 文件名匹配 | 删除同名回退，避免多个 Game.exe 误控 |
| 暂停和删除 | 可能留下已经设置的静音 | 停止拥有对应会话，并恢复原静音状态 |
| 退出 | UI 线程抢先取消静音，工作线程尚未退出，存在再次静音竞态 | 工作线程停止循环后统一恢复并释放 COM，主线程等待其结束 |
| UI 跨线程 | 工作线程和托盘线程直接调用 Tk after | Queue 传递值和回调，由 Tk 主线程统一处理 |
| 配置 | 每次读取磁盘；非原子写；异常时返回空配置；README 路径不符 | 内存快照和锁、原子替换、损坏时报错；兼容实际旧配置位置 |
| 图标资源 | GDI 位图/DC 资源释放不完整 | 确定性释放 HICON、bitmap、memory DC、screen DC，并限制缓存 |
| 入口/测试 | CLI 和测试引用已删除的 DummyAudio，测试收集失败 | 修复入口和测试适配；正常退出后的恢复也是测试断言 |
| 打包 | 硬编码机器路径、自动升级全局 pip、成功判断不可靠 | 仓库相对路径、固定依赖、失败即返回非零、不修改全局缓存 |

## 3. 重构后的模块关系

```text
Windows 顶层窗口 → windows.py → picker.py → Config
进程/前台/最小化 → WinFocus → Service → GameState
                                      ├─ Queue → app_gui.py → Tray
                                      └─ PycawAudio → 播放端点和会话
                                                       └─ 恢复记录
```

保留 Tk、pystray、pycaw 技术栈，避免同时引入 UI 框架迁移。多游戏采用一个后台服务而非多个独立 exe：各游戏独立持有状态，设备枚举和线程退出只需要一套协调机制，也避免多个控制器争抢同一音频会话。

### 任务栏选择

使用可见顶层窗口、owner、WS_EX_APPWINDOW、WS_EX_TOOLWINDOW、WS_EX_NOACTIVATE、DWM cloaked 等窗口属性判断任务栏候选，不对游戏类型或前台状态评分。最小化窗口仍可列出；只有固定图标但未启动的应用没有可控进程，因此不列入。一个 exe 的多窗口只显示一张卡片。

网格不展示完整路径，选择在搜索和定时刷新后保留，取消不修改配置。特殊宿主程序或 helper 音频进程可通过文件添加。

### 多游戏状态

| 操作/事件 | A | B |
| --- | --- | --- |
| A、B 都启动 | 各自图标和策略 | 各自图标和策略 |
| 暂停 A | 恢复 A 的原静音状态，图标保留并标注暂停 | 不变 |
| 停止 A 控制（本次） | 恢复 A 并移除 A 图标，库中记录保留 | 不变 |
| A 退出 | 移除 A 图标并清理/恢复其旧会话 | 不变 |
| A 再次启动 | 自动重新接管并创建图标 | 不变 |
| 暂停全部 | 恢复可访问的会话 | 恢复可访问的会话 |
| 退出全部 | 服务停止后统一恢复，移除全部图标 | 同左 |

“本次停止”可在游戏库点击继续提前恢复；否则在检测到游戏退出并再次启动后恢复。图标按 exe 路径区分，同一 exe 的多个实例合并控制。Windows 负责图标排列和折叠，应用不会强制修改系统托盘设置。

### 音频恢复与设备变化

- 会话身份包含端点 ID 和 session instance ID，不会把不同设备上的同一进程混在一起。
- 静音之前保存原静音位，不改变音量 scalar，也不改变默认设备。
- 每约 0.5 秒扫描所有可用输出端点。切换默认设备、USB/蓝牙重新连接、新建会话都在相同机制下重试。
- 一个端点失败仍处理已成功枚举的其他端点；错误显示在主界面。
- 原子恢复记录先落盘再调用 SetMute。异常重启后，如果同一会话仍存在，可以继续沿用原基线。
- 离线设备的原状态保留在恢复记录中；不假装离线会话已经恢复。
- 清理消失的会话前仍尝试恢复旧 COM handle，防止静音状态泄漏到下一次启动。
- COM 引用在所属工作线程释放后才调用 CoUninitialize。

采用短周期重枚举而非额外维护设备回调线程，使设备、音频服务和会话重新出现时使用相同恢复路径。这里是最终一致的自动恢复，不保证设备切换时零延迟。

### 原生 Windows：8 个生命周期场景通过

`tests/windows_audio_smoke.py` 使用两个独立 exe 的 WinForms 窗口和真实 Core Audio 会话。音频数据是全零的无声 WAV，不播放提示音，也不操作其他应用的会话。

1. 只启动 A：一个原生托盘图标。
2. 后启动 B：自动增加第二个图标，后台 A 的真实会话静音。
3. 暂停 A：A 恢复。
4. 停止 A 控制：只剩 B 的图标，B 继续管理。
5. 关闭 A：B 不受影响。
6. 重启 A：图标回来，前次静音没有遗留。
7. 暂停全部：剩余会话恢复。

测试程序先为自己的会话设置已知基线，因为 Windows 会记住测试 exe 上次的混合器状态。测试不会以“当前状态本来是什么”替代明确前置条件。

## 7. 明确保留的边界

- 已验证设备切换和失效恢复的模拟场景，并在本机读取两个实际输出设备。没有为了测试去改动当前默认声卡、物理拔插耳机、重启 Windows Audio 服务；不声称完成这些破坏性实机操作。
- 无声 fixture 验证真实 Core Audio 静音位，不代表检查了每款游戏的实际听感。
- 强制杀进程、系统崩溃、断电无法保证即时取消静音；恢复依赖下次运行及对应会话仍可访问。
- 消失的端点和已经销毁的会话无法被强行恢复。
- 音频由独立 helper 发出时需登记 helper；不会用同名猜测控制其他进程。
- 特殊 Shell/UWP 托管窗口、独占输出或绕过 Windows 常规会话的音频仍可能需要特定适配。
- 托盘图标是否在折叠菜单中、是否相邻，由 Windows 管理。
- 轮询周期默认 0.5 秒，检测和恢复有这一量级的延迟。
- 同一路径多实例合并管理；不同路径的游戏各自独立。

## 8. 实现依据

任务栏筛选依据 [Microsoft Taskbar 文档](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar) 和 [DWM 窗口属性](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)。

设备和会话枚举依据 [EnumAudioEndpoints](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immdeviceenumerator-enumaudioendpoints)、[GetSessionEnumerator](https://learn.microsoft.com/en-us/windows/win32/api/audiopolicy/nf-audiopolicy-iaudiosessionmanager2-getsessionenumerator) 及当前安装的 pycaw 实现。设备变化类型参见 [Core Audio Device Events](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-events)；本实现选择周期重枚举而非通知回调。
